Fokus lessons · Lesson 0001

The map of the app

How fokus-android is organized, and the single mental model that explains all of it: events flow down, state flows up.

Your win after this lesson

You can open this repo, name every piece of it, say what each piece does, and trace one button tap from the screen through the service into the timer engine and back. Everything else — Compose, services, persistence — will hang off this one picture.

1 · An Android app is a set of OS-managed components

In a language like Python or JavaScript, a program has one entry point and runs top to bottom. An Android app is different: it is a bundle of components that the operating system can start and stop on its own — when you open the app, when the phone reboots, when a notification is tapped. The OS needs a map of these components, and that map is AndroidManifest.xml.

Open it now: app/src/main/AndroidManifest.xml. Every app ships one, and it is always worth reading first, because it tells you what the app is to the system:

app/src/main/AndroidManifest.xmlThe app's contract with the OS.

It declares three components and the permissions they need:

  • MainActivity (line 19) — the launcher screen. Its intent-filter with MAIN/LAUNCHER tells Android "this is the screen to show when the user taps the app icon."
  • FokusService (line 28) — background work with no UI. It is the heart of the app, keeping the countdown alive.
  • BootReceiver (line 37) — a listener that gets woken up after a reboot and restarts the service.

The permissions (lines 4–9) are capabilities the app is requesting: show notifications (POST_NOTIFICATIONS), draw over other apps (SYSTEM_ALERT_WINDOW), run as a foreground service, and so on.

Key idea

An Android app is not one program — it is a set of entry points the system can invoke. The manifest is the list. Reading the manifest first is the fastest way to learn what any app does.

2 · The layered picture of Fokus

Inside the components, the code is arranged in layers, from the screen down to the pure logic. This matches the pattern the official architecture guide recommends (developer.android.com/topic/architecture): a UI layer, state holders, and a data layer with the business logic.

┌──────────────────────────────────────────────────────────────────┐
│  UI layer   TimerScreen.kt  ·  SettingsScreen.kt  ·  TimerFace.kt │
│             (Jetpack Compose — screens read state, send events)  │
└───────────────────────────────┬──────────────────────────────────┘
                                │ binds + observes
┌───────────────────────────────▼──────────────────────────────────┐
│  State holder  TimerViewModel.kt                                 │
│                (bridges UI ↔ service; reads SettingsRepository)  │
└───────────────────────────────┬──────────────────────────────────┘
                                │ bound service (Binder)
┌───────────────────────────────▼──────────────────────────────────┐
│  Service  FokusService.kt  — foreground, sticky, owns:           │
│            · tick loop (delay 250 ms)                            │
│            · persistent notification · break overlay             │
│            · session persistence (SharedPreferences)             │
└───────────────────────────────┬──────────────────────────────────┘
                                │ drives
┌───────────────────────────────▼──────────────────────────────────┐
│  Pure logic  TimerEngine.kt  — the Pomodoro state machine        │
│              (no Android imports; injected clock → unit-tested)  │
└──────────────────────────────────────────────────────────────────┘

Side branches:
  SettingsRepository.kt — DataStore-backed settings (exposed as a Flow)
  OverlayController.kt — full-screen break overlay via WindowManager
  BootReceiver.kt      — restarts the service after reboot

The interesting design choice: the engine is plain Kotlin with no Android dependency (app/src/main/java/dev/fokus/app/timer/TimerEngine.kt:1). It even takes its clock as a parameter — clock: () -> Long — so tests can control time. That is why the repo can unit-test the entire Pomodoro behavior on a JVM without a phone: app/src/test/java/dev/fokus/app/timer/TimerEngineTest.kt.

This layering is a deliberate, learnable pattern: keep the rules pure and testable, wrap them in Android machinery, and let state flow out to whoever needs it.

3 · Trace: what happens when you tap “Start”

Here is the payoff. Follow one tap through the whole app. The files, in order:

TimerScreen.kt:188The Start button. onClick = onStart → viewModel.start().
TimerViewModel.kt:66fun start() = service?.startFocus() — forwards the event to the bound service.
FokusService.kt:210startFocus() = dispatch { engine.start() } — the service owns the engine.
TimerEngine.kt:130start() — sets running = true and deadlineMs = now + focus length.

Then the state must come back up:

FokusService.kt:232publish() — _state.value = engine.snapshot(); the service's StateFlow<Snapshot> updates.
TimerViewModel.kt:45A coroutine collects the service state into the ViewModel's own _snapshot.
TimerScreen.kt:57val snapshot by viewModel.snapshot.collectAsState() — Compose re-renders with the new time.

And meanwhile, a tick loop keeps the clock moving: a coroutine in the service calls engine.tick() every 250 ms (FokusService.kt:141). When a session's deadline passes, tick returns an event — break started, focus started, overtime began — and the service turns events into notifications and state updates.

tap "Start"
   │  (event, downward)
   ▼
TimerScreen ──▶ TimerViewModel ──▶ FokusService ──▶ TimerEngine.start()
                                                       │ sets deadline
                                                       ▼
                          tick loop (every 250 ms) ──▶ TimerEngine.tick()
                                                       │ deadline passed?
                                                       ▼
                                state: StateFlow<Snapshot>  (state, upward)
   │
   ▼
TimerScreen recomposes ──▶ dial shows 25:00 ──▶ … and 24:59 next second
Key idea

Events flow down, state flows up. User actions travel down through ViewModel and service into the engine; the engine's Snapshot flows back up through the same layers, and any screen observing it updates itself. Nothing mutates state from the UI directly.

4 · Do it yourself (2 minutes)

Strengthen the map in your head — no coding, just reading. In an editor, open these and confirm the claims:

  1. FokusService.kt:232 — find publish() and see that it sets _state.value and toggles the overlay.
  2. TimerEngine.kt:113 — find snapshot(); notice it derives everything from stateVal, deadlineMs, and the durations. That is the single source of truth.
  3. TimerViewModel.kt:54 — find init: the ViewModel starts the service and binds to it the moment it's created.
